Implementation plan

Mortgage POC Build Plan

Turning the AI-Native Mortgage design into a working system — React, FastAPI, SQLite, and Claude Opus 4.7 on Microsoft Foundry — with real agents, gated tools, enforced constraints, memory and an auditable trail.

React 18 + Vite FastAPI + SQLModel SQLite claude-opus-4-7 Microsoft Foundry Docker → Azure Web App
Part 00

Three findings that shape the plan

Managed Agents is not available on Microsoft Foundry

Anthropic's server-managed agent runtime — where Anthropic hosts the agent loop and a per-session sandbox — does not run on Foundry. Neither do Message Batches or the Models API.

So the agent loop is ours to own: Claude API + tool use, hosted in our FastAPI container. That is genuinely the better fit here anyway — we need every tool call intercepted, gated and written to an audit table, and a self-hosted loop gives us that chokepoint. But it does mean the loop, the retries and the state persistence are code we write, not a platform feature we configure.

Several features are beta on Foundry — verify before designing around them

Messages, streaming and tool use are GA on Foundry. These are beta there: structured outputs / strict tool use, adaptive thinking and effort, prompt caching, the memory tool, the 1M context window, and the Files API. They are all in the plan below, but day one is a spike that confirms which betas your Foundry deployment actually accepts — the fallbacks are noted where it matters.

Claude Opus 4.7 has a different request shape than you may expect

claude-opus-4-7 is correct and current — 1M context, $5/$25 per million tokens, billed through Microsoft Marketplace at standard rates. Three API details will bite otherwise:

  • budget_tokens is removed — sending it returns a 400. Use thinking={"type": "adaptive"} and control depth with output_config={"effort": …}.
  • Omitting thinking entirely means the model runs without thinking on 4.7. It must be set explicitly.
  • Assistant prefill returns a 400. Shape output with structured outputs or the system prompt instead.
Part 01

What the POC does, and what it deliberately does not

The slice worth building is the one where a model does real work. That is intake → validation → exception with a real confidence score → disposition → queue → underwriter decision. Everything else is scaffolding around that.

In the POCOut of the POC
Real document classification and field extraction from synthetic PDFs Closing & Funding, Post-Closing QC screens
Model-generated exceptions with genuine, calibratable confidence Any integration with a real loan origination system
Deterministic disposition policy, HITL queues, supervisor sign-off Real vendor ordering, real borrower email
Underwriters' Hub with model-written document summaries Multi-tenancy, SSO, production identity
Hash-chained audit trail, live SSE agent log Fair-lending monitoring, model risk governance
Tool gating, constraint enforcement, per-run budgets Horizontal scale — one container, one worker

The demo story stays identical to the MVP, so nobody has to relearn it. The difference is that the exceptions are now discovered rather than seeded — and you can prove it by dropping a new synthetic loan into the system live and watching the agents find things nobody wrote down in advance. That is the moment worth engineering for.

Part 02

Architecture

┌─────────────────────────────────────────────────────────────┐ │ React 18 + Vite (the MVP's six screens, ported) │ │ fetch → /api/* EventSource → /api/runs/{id}/events └──────────────────────────┬──────────────────────────────────┘ │ served as static files by FastAPI ┌──────────────────────────▼──────────────────────────────────┐ │ FastAPI │ │ │ │ routes/ thin — auth, validation, no logic │ │ orchestrator/ run lifecycle, stage sequencing, SSE bus │ │ agents/ 4 LLM agents + 3 deterministic │ │ tools/ registry · JSON schemas · handlers │ │ gate.py ◀── EVERY tool call passes through here │ │ policy.py disposition thresholds, invariants │ │ audit.py append-only, hash-chained │ │ llm.py AnthropicFoundry client, caching, retries │ └───────┬──────────────────────────────────┬──────────────────┘ │ │ ┌───────▼────────────┐ ┌───────────▼──────────────────┐ │ SQLite (SQLModel) │ │ Microsoft Foundry │ │ loans exceptions │ │ claude-opus-4-7 │ │ runs turns docs │ │ 1M ctx · adaptive thinking │ │ approvals audit │ └──────────────────────────────┘ │ memory_notes │ └────────────────────┘

Why these choices

FastAPI
Async, and Pydantic-native — the same Pydantic models define the API schema and the model's structured output schema. One definition of an Exception, used in three places. Server-Sent Events give the live agent log that makes the demo land.
SQLModel
SQLAlchemy + Pydantic in one class. Avoids maintaining ORM models and API schemas separately in a POC.
SQLite, container-local
See the note below — this is a decision, not a default.
One container
FastAPI serves the built React bundle as static files. A single image, a single Azure Web App, no CORS, no separate frontend deploy.
SQLite on Azure App Service — do not put it in /home

App Service's persistent /home is an SMB-mounted Azure Files share. SQLite's locking behaves badly over SMB and will produce intermittent database is locked errors under any concurrency.

Put the database on the container's local disk and seed it at startup. For a demo this is not a compromise, it is a feature: every container restart is a guaranteed-clean demo, and the Reset Demo button just re-runs the seeder. Treat the data as ephemeral by design, and say so. When the POC graduates, swap SQLModel's connection string for Azure Database for PostgreSQL — that is a one-line change plus a migration.

Data model

The MVP's shapes carry over unchanged — do not renegotiate the vocabulary — plus four new tables the real system needs:

  • documents — synthetic PDFs per loan, with extracted fields and per-field confidence.
  • runs and turns — every agent invocation, its messages, token usage, latency and cost. This is what makes the loop resumable and the spend visible.
  • audit — append-only, each row carrying a SHA-256 of the previous row.
  • memory_notes — cross-run operational memory (Part 06).
Part 03

Agents

Seven named agents in the design. Only four of them should call a model. Using an LLM where arithmetic will do is the most common way a POC like this becomes slow, expensive and non-deterministic for no benefit.

AgentKindWhat it doesEffort
Document IntakeLLM Classifies each document, extracts typed fields, returns a per-field confidence high
ValidationLLM + rules Runs the deterministic rules engine, then reasons over what the rules could not settle — reconciling income across three documents, judging whether a deposit is sourced high
ProcessingLLM Plans and executes the repair for an auto-lane exception medium
Hub SummarizerLLM Writes the income / credit / collateral summaries for the underwriter, with citations back to source documents medium
Risk / AUS Scoringcode DTI, LTV, program caps, AUS finding. Pure arithmetic — a model here adds latency and removes reproducibility—
Workflow Orchestrationcode Routes to a queue by exception type and current load. A lookup and a sort—
Supervisorcode Sequences stages, evaluates readiness, opens and closes runs—

The agent loop

Use the SDK's tool runner rather than hand-writing the loop, and get the audit chokepoint by wrapping each tool function rather than by owning the loop.

# app/llm.py
from anthropic import AnthropicFoundry

client = AnthropicFoundry(
    api_key=settings.foundry_api_key,      # from Key Vault, never in the image
    resource=settings.foundry_resource,
)

MODEL = "claude-opus-4-7"      # exact ID — never append a date suffix
# app/agents/validation.py
from anthropic import beta_tool

def run_validation_agent(loan_id: str, run_id: str) -> list[ExceptionDraft]:
    runner = client.beta.messages.tool_runner(
        model=MODEL,
        max_tokens=16000,
        thinking={"type": "adaptive"},        # explicit — 4.7 does not think by default
        output_config={"effort": "high"},      # judgment work deserves it
        cache_control={"type": "ephemeral"},   # caches the guideline pack
        system=build_system_prompt("validation"),
        tools=[t.fn for t in TOOLS.for_agent("validation")],
        messages=[{"role": "user", "content": build_context_pack(loan_id)}],
    )

    for message in runner:
        if message.stop_reason == "refusal":      # guard before reading content
            audit.record_refusal(run_id, message.stop_details)
            break
        persist_turn(run_id, message)                 # tokens, latency, cost
        if budget.exceeded(run_id):
            raise BudgetExceeded(run_id)
Where the confidence score comes from

The model does not choose the disposition. It returns a finding with a confidence and a severity and its evidence; a deterministic policy function maps those to auto or hitl. That separation is what makes the threshold auditable, tunable and testable without touching a prompt — and it is exactly the knob that decides whether this system is safe. Keep it in code, in one file, under test.

Structured output for findings

One Pydantic model, used as the API schema, the ORM row and the model's output format:

class ExceptionDraft(BaseModel):
    loan_id: str
    stage: Literal[0, 1, 2]
    type: str
    severity: Literal["Low", "Medium", "High", "Critical"]
    confidence: int = Field(ge=0, le=100)
    rationale: str                     # why it was flagged
    evidence_snapshot: str             # the quoted source data
    evidence_doc_id: str | None        # traceable back to a document
    recommended_action: str

response = client.messages.parse(
    model=MODEL, max_tokens=16000,
    thinking={"type": "adaptive"},
    messages=[...],
    output_format=ExceptionFindings,       # a list[ExceptionDraft] wrapper
)
findings = response.parsed_output            # validated, typed

Structured outputs are beta on Foundry. If your deployment rejects them, the fallback is a raise_exception tool with strict: true and additionalProperties: false — same schema guarantee, reached a different way, and arguably better here since it puts findings through the same gate as every other write.

Part 04

Tools

Twelve tools, each a typed function with a JSON schema. The colour is the security posture: read cannot change anything, write mutates our own state, gated costs money or contacts a human and requires explicit confirmation.

ToolPurpose

get_loanreadLoan header — borrowers, program, amount, FICO, DTI, LTV

evaluate_rulereadRuns one deterministic rule and returns pass / fail / indeterminate
lookup_guidelinereadRetrieves the guideline passage for a program and topic
recall_notesreadOperational memory relevant to this exception type (Part 06)
record_extractionwritePersists an extracted field with its confidence and source location
raise_exceptionwriteEmits a finding. The agent's primary output

Note what is not here: no bash, no filesystem, no shell. The design brief calls for a narrow, typed surface precisely so the harness can intercept, gate and audit every action. A bash tool would hand the gate an opaque string and there would be nothing left to enforce.

# app/tools/registry.py — one decorator carries policy + audit

def tool(name, posture, agents, gated=False):
    def wrap(fn):
        @beta_tool
        @functools.wraps(fn)
        def inner(**kwargs):
            ctx = current_run.get()
            gate.check(name, posture, agents, gated, kwargs, ctx)   # raises ToolDenied
            audit.tool_call(ctx.run_id, ctx.agent, name, kwargs)
            try:
                result = fn(**kwargs)
            except Exception as e:
                audit.tool_error(ctx.run_id, name, e)
                return {"error": str(e), "is_error": True}
            policy.assert_invariants(ctx)          # post-condition check
            audit.tool_result(ctx.run_id, name, result)
            return result
        TOOLS.register(name, inner, posture, agents)
        return inner
    return wrap

Part 05

Constraints

Four independent layers. Each catches what the one above it cannot.

1 · Schema — the model cannot express an invalid finding

strict: true with additionalProperties: false, plus Pydantic validation on the way in. A severity outside the enum or a confidence of 140 never reaches the database.

2 · Capability — which agent may call which tool

A static matrix in gate.py. The Validation Agent can raise an exception but cannot repair one. The Processing Agent can repair but cannot raise. The Hub Summarizer has read-only tools and nothing else. This is the same principle the MVP already enforces in its state layer — the tool refuses, not the interface — and it is the primary defence against a prompt-injected document talking an agent into an action.

3 · Policy — the disposition rule and its invariants

# app/policy.py — the whole safety posture, in one testable file

AUTO_THRESHOLD = {                      # per exception type, not one global number
    "missing_document":       88,
    "low_confidence_ocr":     85,
    "flood_determination":    90,
}
NEVER_AUTO = {"income_variance", "dti_breach", "title_exception",
              "identity_mismatch", "appraisal_variance", "undisclosed_debt"}

def decide_disposition(f: ExceptionDraft) -> Disposition:
    if f.severity == "Critical":            return HITL(requires_sup=True)
    if f.type in NEVER_AUTO:               return HITL(requires_sup=is_breach(f))
    if f.confidence >= AUTO_THRESHOLD.get(f.type, 101):  return AUTO
    return HITL()                        # unknown type defaults to a human

Three properties worth keeping: an unknown exception type defaults to a human (the 101 sentinel makes that structural rather than accidental); Critical is never automatic regardless of confidence; and thresholds are per-type, because "88% sure a document is missing" and "88% sure this income is fine" are not the same claim.

Invariants re-checked after every write, rolling back on violation: an agent may never set an exception to resolved if requires_sup; a loan may not be ready while a gating exception is open; every exception must carry evidence traceable to a document.

4 · Budget — the run cannot run away

Per run: max tool calls (30), max tokens (150k), wall-clock (120s), and a dollar ceiling computed from Opus 4.7's $5/$25 rates. Breaching any of them fails the run cleanly and writes an audit line, rather than quietly costing money. Surface spend per loan in the UI — clients ask, and having the answer on screen is unreasonably persuasive.

Part 05b

Loops, and where self-correction belongs

There are four loops in this system and only one of them is driven by a model. Keeping that clear is what makes the behaviour reproducible and the audit trail meaningful.

LoopDriven byBounded by
Tool use (inner)Claude calls a tool, reads the result, decides the next call, until end_turn30 calls / 150k tok / 120s / $1.50
Stage orchestrationPython — for stage in 0..2: for loan in loans:Fixed by the business process
Human in the loopPeople, asynchronously across requests and daysNot a process loop at all
Transport retrySDK, on 429 / 5xx2 retries, exponential backoff

The model never decides what happens next at the macro level. It does not plan the pipeline, pick which loan to work, or judge when a stage is finished. Mortgage origination has a known sequence, so autonomy is confined to within a stage — "how do I investigate this loan's income?" — never "what should the system do now?" An agent that re-plans the process on each run is a system you cannot test.

A trap, if you later add web search

The Python tool runner does not auto-resume a pause_turn — it exits silently and hands back a truncated answer with no error raised. That only happens with server-side tools. Every tool in this plan is client-side, so it cannot occur today. Add web search for guideline lookup and it becomes real, and needs the mirror-history, restart-the-runner pattern.

Self-correction: skip the reflection pass

A generic "review your answer and revise it" step is not worth having here. Models are unreliable judges of their own output, it doubles cost and latency, and it introduces drift — the model talking itself out of a correct finding. Three mechanisms already in the design are strictly better:

Deterministic verification
Do not ask the model to check its arithmetic — compute DTI in Python. Do not ask "are you sure that document is missing?" — query the table. Anything code can verify, code verifies. That is grounding, not reflection.
Evidence binding
Every finding cites a document id and a quoted span; a validator confirms the quote actually appears in that document. Hallucinated findings are rejected mechanically, with no second model call and no judgement involved.
The HITL lane
Low confidence routes to a person. That is the correction loop, and a human correcting the machine is auditable in a way self-critique never is.

Where bounded correction does earn its place

  • Tool-error feedback. A denied or failed tool returns is_error: true with a reason, and the model adapts. This is self-correction of the useful kind — driven by a real signal rather than introspection.
  • Validator-driven repair. When the evidence validator rejects a finding, feed the rejection back once. Then fail the finding.
  • Re-extraction on low confidence. Re-read with different input — higher resolution, or cross-referenced against a second document. A retry with new evidence, not "think harder about the same thing." It mirrors the design's own Re-OCR at 300dpi exception.
The rule that keeps the threshold meaningful

Confidence may never be revised upward, and no correction may move a finding from HITL to auto. Confidence is the number the entire safety threshold rests on. If a second pass could move a finding from 62% to 89%, the gate would be decorative and the auto lane would silently widen. First-pass confidence is the ceiling; deterministic checks may only lower it. Enforced in policy.revise_confidence() and policy.revise_disposition(), both of which raise rather than clamp — a silent clamp would hide the bug that caused it.

The correction that actually compounds is offline: ground_truth.json lets you tune thresholds, revise prompts and retire bad exception types between runs. That improvement is measurable. A runtime critique pass is not.

Part 06

Memory and context

Context assembly

Every request is built by one build_context_pack() function, in strict cache order — tools → system → messages, most stable first:

  1. Tool definitions — deterministic order, never sorted differently between runs.
  2. System prompt — the agent's role, its constraints, its output contract. Frozen.
  3. The guideline pack for the loan's program — large, identical across every loan of that program. This is the cache win.
  4. Cache breakpoint here.
  5. Loan snapshot, extracted fields so far, recalled notes — volatile, after the breakpoint.

Verify it is working by asserting usage.cache_read_input_tokens > 0 on the second and later loans in a run. If it is zero, something volatile has crept above the breakpoint — a timestamp in the system prompt is the classic culprit. Make that assertion a test, not a hope.

Two kinds of memory, deliberately separated

Case memory
SQLite
What we know about this loan — extracted fields, findings, resolutions, who did what. Structured rows, not files: queryable, joinable, auditable, and it is the same data the UI renders. Loaded into the context pack as a compact JSON block.
Operational memory
memory tool
What we have learned across loans — "flood-zone mismatches from this vendor resolve on re-pull in 94% of cases", "this employer's paystubs put YTD in an unusual field". Rule-shaped generalisations that make the next run better. This is where Anthropic's memory_20250818 tool fits, with the model reading and writing its own notes.
The memory rule that must not be broken

No borrower data in operational memory. Ever. Memory files persist outside the loan record, outside its retention policy, and outside the audit trail that governs it. A note saying "employer Acme reports YTD in box 14" is a useful generalisation. A note saying "David Chen's paystub shows $6,520/mo" is an uncontrolled copy of financial PII.

Enforce it, do not document it: run a PII detector in the memory write handler and reject anything containing a name, an account number, an SSN pattern or a specific dollar figure tied to a person. The memory tool is client-side — the handler is ours, so the check is ours to make.

Long conversations

Each agent run here is short — five to ten tool calls — so neither compaction nor context editing is needed at POC scale. If the Validation Agent ends up reading many long documents in one run, reach for context editing first (clear_tool_uses_20250919, beta context-management-2025-06-27), which prunes stale tool results without summarising anything away. Both are beta on Foundry — check before relying on them.

Part 07

Security

Secrets

The Foundry key lives in Azure Key Vault, surfaced to the app as a Key Vault reference in App Service settings (@Microsoft.KeyVault(SecretUri=…)) and read by the container's system-assigned managed identity. It is never in the image, never in the repo, never in an environment variable committed anywhere. Verify by grepping the built image.

Prompt injection — the documents are hostile input

A synthetic PDF is a benign stand-in for a document a borrower uploads, which in production is attacker-controlled. Three defences, in order of how much they actually matter:

  1. The capability matrix. If an injected instruction persuades the Validation Agent to call apply_auto_repair, the gate denies it — that agent does not have that tool. This is the defence that works; the other two are hygiene.
  2. Delimiting. Document text is wrapped and labelled as untrusted data with an explicit instruction that content inside is never an instruction.
  3. Output validation. Every finding must cite a document id and a quoted span; a finding that cannot be traced back to source text is rejected before it is stored.

Identity and authorisation

Five demo personas behind a signed JWT. Every endpoint re-checks the role server-side — the same rule the MVP already follows, now across an HTTP boundary where it actually matters. The React app hides controls for convenience; the API refuses for correctness.

Tamper-evident audit

Each audit row stores hash = sha256(prev_hash ‖ canonical_json(row)). A /api/audit/verify endpoint walks the chain and reports the first break. Cheap to build, and it turns "we log everything" into something a compliance reviewer can check in front of you — which is a materially different conversation.

Container and transport

Non-root user in the image, HTTPS-only enforced on the Web App, no inbound except 443, request size caps on upload endpoints, and per-persona rate limits so a demo cannot accidentally spend the month's token budget.

Data

Synthetic data only — no real borrower ever touches this POC. That is not a limitation to apologise for; it is the control that makes everything above sufficient at this stage.

Part 08

Synthetic data

I will research current market conditions and generate the dataset from them, so the numbers survive contact with someone who knows the industry. What I need to look up:

  • Current conforming loan limit and FHA county limits — these set what counts as Jumbo, and getting them wrong is the first thing a mortgage person notices.
  • Prevailing 30-year fixed, FHA and VA rates.
  • Regional median prices for the metros in the book, so loan amounts are plausible against the property.
  • Realistic FICO, DTI and LTV distributions by program.
  • Observed frequencies of common exception types, so the auto/HITL mix is not invented.

Then a generator produces, for each of ~12 loans:

  • A loan header consistent with its program's real limits.
  • Actual documents as PDFs — 1003, W-2, paystubs, bank statements, credit report, appraisal, title commitment — with the numbers internally consistent, because the Validation Agent's whole job is finding where they are not.
  • Planted defects the agents must discover, not be told about: an income figure that does not reconcile, a DTI that breaches its program cap, a deposit with no payroll trail, a lien on a title commitment.
  • A ground_truth.json that never enters a prompt and exists only to score the agents — recall against planted defects, precision against invented ones, and per-type confidence calibration. This is what turns the demo into an evaluation harness, and it costs almost nothing to produce alongside the data.

Some documents should be scanned-looking rather than clean digital PDFs, or the intake agent's confidence scores will all sit at 0.99 and the auto/HITL split will never be exercised.

Part 10

Build sequence

Step 1 · half a day
Foundry spike — before anything else

One script, one loan, one real call. Confirm the key works, claude-opus-4-7 resolves, and — critically — which betas your deployment accepts: structured outputs, prompt caching, adaptive thinking, the memory tool. Everything downstream assumes an answer here, so get it before writing the architecture around a guess.

Step 2
Synthetic data with ground truth

Market research, then the generator, then the PDFs and ground_truth.json. Doing this early means every later step has something real to run against.

Step 3
Backend skeleton

FastAPI, SQLModel, the schema, the seeder, the audit chain, and the deterministic pieces — rules engine, DTI/LTV, routing, readiness. No model calls yet. The MVP's logic ports almost directly.

Step 4
Tools, gate, policy

The twelve tools, the capability matrix, the disposition function, the invariants, the budgets. Written before the agents, and tested without a model in the loop — the gate must be provably correct before anything autonomous is pointed at it.

Step 5
The four LLM agents

Intake first (most visible payoff), then Validation, then Processing, then the Hub Summarizer. Score each against ground truth as it lands.

Step 6
React port + SSE

The MVP's six screens against the real API, with the live agent log driven by Server-Sent Events instead of a timer. The design work is done — this is wiring.

Step 7
Evaluation pass

Recall, precision and confidence calibration per exception type against ground truth. Tune AUTO_THRESHOLD on evidence. This is the step that separates a demo from a credible POC — and the artefact clients' risk teams will actually ask for.

Step 8
Containerise and deploy

Dockerfile, ACR, Web App, Key Vault, health check, a rehearsed demo run on the deployed URL rather than on a laptop.

The one thing to get right

Steps 4 and 7 are what make this a POC rather than a prettier demo. The gate proves the system cannot do what it should not; the evaluation proves it does what it claims. Both are unglamorous, and both are what a client's risk function will ask about within ten minutes of being impressed by the interface.
